# Changelog Archive: v0.21.1 – v0.40.0

Archived entries from [CHANGELOG.md](../CHANGELOG.md), oldest read at the top or bottom the
same as the main file — nothing reordered, just moved. Format is unchanged: [Keep a
Changelog](https://keepachangelog.com/en/1.1.0/) / [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.40.0] - 2026-08-11

### Fixed

- Dragging the per-camera Playback timeline could feel unresponsive, because a page-level
  recenter call fought the drag every 500ms. It now ignores programmatic recentering while that
  timeline is being actively dragged.

## [0.39.0] - 2026-08-11

### Changed

- Live tiles no longer use native browser video controls, since native controls' click-to-pause
  behavior made an accidental click interrupt a continuous live stream for no reason. Replaced
  with a minimal custom hover overlay (mute, fullscreen).

## [0.38.0] - 2026-08-11

### Fixed

- Playback video tiles could grow past their allocated space and cover the timeline below them,
  most visibly with a portrait camera, because grid items don't shrink below their content's
  intrinsic size by default.
- A non-16:9 camera's video was stretched on the Live page, from a missing object-fit style.
- Timeline coverage bars showed as thin alternating stripes instead of solid blocks, from
  sub-pixel rounding gaps between adjacent same-colored buckets; now merged into single fill runs.

## [0.37.0] - 2026-08-11

### Fixed

- Critical: every node process restart could silently delete real, already-recorded footage that
  already had valid database rows. A Motion-mode camera's full on-disk rescan on restart re-fired
  completion events for old files with no memory of what the server already knew about, and a
  freshly-restarted motion session had observed no motion yet, so nearly all of that re-fired
  history was discarded as if it were new and motion-free. The node now pre-seeds its known-files
  tracking from what the server already has rows for, so a file is never re-evaluated across a
  restart. Footage already lost before this fix cannot be recovered. **LarisVMS.Node change —
  install-node.ps1 re-run needed on every recorder node.**

## [0.36.0] - 2026-08-11

### Fixed

- A camera-pushed ONVIF motion event could stop keeping recorded segments partway through a long
  motion event, before the camera reported motion had stopped, because the gating check was keyed
  off how recently the last notification arrived rather than whether the span was still open. Many
  real cameras send only one notification per edge, not a periodic heartbeat. Recording now stays
  retained continuously from the rising event through to the falling event regardless of how
  sparse notifications are in between. **LarisVMS.Node change — install-node.ps1 re-run needed on
  every recorder node.**

## [0.35.0] - 2026-08-11

### Added

- A recorder node now subscribes to a camera's ONVIF PullPoint events and polls for
  notifications, for any camera whose capability probe found an Events service.
- Motion-classified events now drive the same Motion-mode recording gate and timeline coloring a
  server-side motion zone already does, so a camera relying only on onboard detection now gates
  recording correctly too.
- Every raw notification is logged to a new table, not just motion — no dedicated viewer page yet.

### Known limitations

- Unverified against a real camera; ONVIF PullPoint topic naming varies significantly by vendor.

**This is a LarisVMS.Node change — install-node.ps1 re-run needed on every recorder node.**

## [0.34.0] - 2026-08-10

User-directed Playback redesign: move the timeline to the bottom of the page, fill the rest of
the window with video sized to camera count, and make the timeline more compact and scale-aware.

### Changed

- Playback layout: timeline pinned to the bottom of the viewport, video grid auto-sized to camera
  count and window size, independent of any saved view layout.
- Timeline bar redesign: height halved, with tick marks and scale-appropriate labels replacing
  the old two-corner-label footer.

## [0.33.0] - 2026-08-10

### Changed

- Live tiles now show native browser video controls on hover, hidden otherwise, replacing a
  custom mute button.

### Fixed

- A Live camera could intermittently go blank with no error then resume on its own, when playback
  drifted into a portion of the sliding MSE buffer the node had already evicted for a slow client.
  The existing "seek to live edge" recovery now also applies whenever this happens mid-session,
  not just at startup.

### Investigated, not changed

- The intermittent self-recovering decode error is expected behavior, not a bug — the visible
  side effect of the same slow-client fragment-drop described above.

## [0.32.0] - 2026-08-10

### Fixed

- Motion-mode segments with real, detected motion in them were still being discarded, because the
  keep/discard check's lookback window was anchored to the segment's end rather than its start,
  making motion earlier in the segment invisible to it. Masked by the original post-roll default
  until a shorter one was configured. **LarisVMS.Node change — install-node.ps1 re-run needed on
  every recorder node.**

## [0.31.0] - 2026-08-10

### Added

- Admin/Settings: one page for every global setting that can be overridden per node or per
  camera, including recording mode and pre/post-roll (previously only reachable as a per-camera
  override with no visible base default), storage root path, and the node registration key
  (viewable, editable, and rotatable for the first time). Replaces Admin/Retention.

## [0.30.0] - 2026-08-10

### Fixed

- Timeline drag could get permanently stuck to the cursor if the mouse button was released
  outside the browser window. Switched to Pointer Events with capture, which also makes the
  timeline draggable on touch devices for the first time.
- Cameras/Edit had no way to reach the Zones editor once a zone already existed.

### Added

- StorageManager now reconciles its own Segments rows against disk on an hourly cadence.
  Investigation found roughly a third of all Segments rows across both nodes pointed at files no
  longer on disk — a deletion-report failure that was never retried before. Self-healing going
  forward.

### Known limitations

- The reconciliation sweep clears an existing backlog gradually over its hourly cadence, not
  instantly on deploy.

## [0.29.0] - 2026-08-09

### Fixed

- Motion-mode recording gate never re-read config after a camera's session started, because the
  event handler captured that moment's config by reference in a closure instead of looking it up
  fresh. Any settings change to recording mode or pre/post-roll on an already-running camera had
  zero effect until its session happened to restart for an unrelated reason. Now takes effect
  immediately for already-running sessions.

## [0.28.0] - 2026-08-09

### Changed

- Default zone sensitivity lowered from 15% to 3%, after measuring real captured frames from a
  real outdoor camera showed genuine motion topping out far below the old threshold. The motion
  pipeline itself was working correctly; only the number was wrong.

### Known limitations

- Does not retroactively update zones already saved with the old default; existing zones need
  manual adjustment.

## [0.27.0] - 2026-08-09

### Fixed

- A missing segment (404) triggered a burst of repeated identical requests during a scrub drag,
  since a failed fetch was never remembered. A 404'd segment id is now remembered for the rest of
  the page load; a 5xx is still retried.
- StorageManager could permanently orphan a Segments row if its best-effort deletion report ever
  failed, since nothing retried it and the file was already gone by the next sweep. Deletion
  reports are now retried until they succeed.

### Known limitations

- Does not clean up rows already orphaned before this fix.

## [0.26.0] - 2026-08-09

### Fixed

- The previous release's checkpoint reporting fix wasn't enough — segment retention only required
  recent motion activity, not a confirmed span, so frequent short motion bursts were correctly
  retained on the timeline as blue-only with no green ever reported. Checkpointing now reports on
  raw recent activity, matching what retention already treats as real.
- The timeline stopped following playback entirely when the starred primary camera stalled, even
  though other tiles kept playing. The shared clock now falls back to any other actively-playing
  tile.

### Changed

- Playback segments now stream into the decoder incrementally instead of waiting for the whole
  file to download first, noticeably reducing time to first frame.
- Tiles ending up far apart in playback position is now corrected by nudging each tile back in
  line with the shared playhead clock when it drifts, on top of the streaming change above.

### Known limitations

- These are the deepest, riskiest changes to the MSE segment-loading path since the original
  design and are unverified against real footage.

## [0.25.0] - 2026-08-09

### Fixed

- A long-running motion span never appeared on the timeline until it eventually closed, since
  reporting only fired on close. Fixed by checkpointing every currently-open span roughly every
  15s instead of waiting for closure.

### Added

- Live-view motion indicator: a red "Motion" badge on a camera's tile while any of its zones has
  an open span, polled every 5s.

### Known limitations

- Still unverified against a real camera.

## [0.24.0] - 2026-08-09

### Fixed

- The previous release's claim that pre-record "falls out for free" from continuous recording was
  wrong — the keep/discard decision was made immediately on segment completion using only motion
  observed so far, so a segment finishing just before motion started was already deleted by the
  time that motion arrived. Real pre-roll requires deferring the decision.

### Changed

- The single padding setting split into separate pre-roll (default 10s) and post-roll (default
  30s) settings.
- A Motion-mode segment's keep/discard decision is now deferred until pre-roll seconds after the
  segment ends, checking for activity across the full pre-roll/post-roll window around it.

### Known limitations

- Still unverified against a real camera.

## [0.23.0] - 2026-08-09

### Added

- `Recording.Mode` setting (Continuous | Motion), resolved per camera. Only these two modes exist
  yet; Schedule/Event remain unbuilt.
- `Recording.MotionPaddingSeconds` (default 30): how long after motion stops a segment is still
  kept as context.
- Segment-level gating on the node: a Motion-mode camera still records continuously to disk, but a
  finished segment is now deleted immediately (and never reported, so no database row is created)
  if no zone had activity within the padding window.
- Fails safe: `Recording.Mode` defaults to Continuous, and a Motion-mode camera with no enabled
  zone behaves like Continuous rather than silently deleting everything.

### Known limitations

- Unverified against a real camera — this decides what gets permanently deleted, so the core rule
  is unit tested and biased toward over-keeping on any doubt, but real-footage timing hasn't been
  checked.
- No global admin page yet for Recording.Mode/padding defaults.
- Segment-boundary precision isn't frame-accurate; the decision happens once per segment.

M8 pass 1 also shipped, in the same release: server-side motion detection, zones, and timeline
motion coloring. Camera-side motion push, ONVIF PullPoint event ingestion, and bounding-box
metadata were explicitly deferred.

**Fixed post-release, before this ever deployed successfully:** the initial migration failed — SQL
Server rejected a foreign key for creating a second cascade path alongside an existing one. Fixed
by changing that FK to Restrict and moving the null-out into application code instead of a DB-level
cascade.

### Added

- Zones (Pages/Cameras/Zones): one polygon editor for all four zone kinds (Motion-server, Ignore,
  Motion-camera, Privacy), drawn on a live camera snapshot.
- Snapshot capture: a one-shot still-frame grab from a camera's Main stream, proxied through the
  web tier.
- Server-side motion detection: a node opens a second RTSP session against a camera's Sub stream,
  diffs consecutive frames per enabled zone, and reports completed motion spans to the web tier.
- Timeline motion coloring: buckets with motion render bright green, taking priority over blue for
  a bucket with both.

### Known limitations

- Motion is detected and shown on the timeline but does not yet control recording.
- Camera-pushed (ONVIF) motion zones and privacy zone burn-in do nothing yet — stored only.
- No ONVIF PullPoint event ingestion yet.
- Unverified against a real camera and browser; Sub-stream RTSP is new ground in this codebase.

## [0.21.2] - 2026-08-09

### Added

- `fix-legacy-segments.ps1`, repairing footage recorded before the 0.21.1 recorder fix so it plays
  back in a browser — rewrites each affected segment's container in place with no re-encode. Dry
  run by default, idempotent, and safe to run against a live node.

### Changed

- `deploy.ps1` now builds the recorder node package as part of every web deploy instead of relying
  on a separate manual step.

### Fixed

- Corrected a doc comment that misattributed a prior playback bug to query-string date parsing;
  the real cause was the recorder's muxer flags (see 0.21.1).
- Corrected `install-node.ps1`'s warning that LocalSystem cannot access network storage — it can,
  once the machine account is granted share/NTFS permissions.

## [0.21.1] - 2026-08-09

### Fixed

- Recorded segments could not be decoded by a browser at all, which is why Playback never showed
  video — the recorder's dual-output ffmpeg pipeline set a required MSE flag on the live-view leg
  but not the segment-file leg. Only newly recorded segments are affected; footage already on disk
  stays unplayable in-browser (still valid MP4 in a normal player) until re-recorded.

**This is a `LarisVMS.Node` change** — re-run `install-node.ps1` on every recorder node for it to
take effect.
